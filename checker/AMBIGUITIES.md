# Ambiguities, gaps and property problems found in workflow_semantics_v1

Each item: what the spec leaves open, what `run.py` / `validate.py` choose, and which of the 64 scenarios could be affected. "None" means no provided scenario exercises it, so the choice cannot change any of the 64 outputs. Items 1 and 2 are the ones that matter most.

## A. Spec properties that do not hold under sections 7 to 9

1. **Property 5 (queue order) is false under the literal section 8 rule when an activation is created by a zero-length task at the same instant.**
   Section 8 says a new activation "is compared with the rest by the same key, even if it sorts before the activation just dispatched". Take one case with parallel tasks A (key T_c) and X (key T_d) enabled at the same time `e`. X is in another pool and has service 0, and its successor B (task id T_b) is in A's pool. Dispatch order is A, then X (which creates B), then B. B's key is smaller than A's, but B starts after A (A holds the only instance). So "a smaller key never starts later than a larger key" fails. The same counterexample breaks a "dispatch in sorted key order" reading of section 8.
   Reproduced in `checker/tests/tie.bpmn`, `tie.json`, `tie_scn.json`. `run.py` follows the section 8 dispatch semantics, and its output fails validator property P5 and my sorted-key replay (`X_section8_definition_replay`) on that test only. It needs the same case, a shared pool, and a zero-length task, so it cannot occur in cross-case ties. None of the 64 scenarios triggers it; all pass.
   Proposed fix: state property 5 as "among activations that exist at the moment of dispatch" or order by (creation, key).
2. **Equivalence of the time-stepped scheduler and section 8.** The argument relies on a new activation's `enabled` being at least the `enabled` of the activation that created it (true, since `end >= start >= enabled`), so dispatch order is chronological except for same-instant ties. As a cross-check the validator replays the literal section 8 loop over the recorded activations in sorted-key order; it agreed on all 64 outputs. It deviates only in the item 1 tie case, where the sorted-key replay (not `run.py`) departs from the definition.

## B. Ambiguities and gaps (choice made)

3. **Which tag identifies "the pool" in `task_resource_distribution`.** The spec says pools are entries of `resource_list`. I match `resources[].resource_id` to the `resource_list` entry `id` (not the profile `id`), and interventions name a pool by the entry `name`. In the published models the profile id differs from the entry id (`..._1`), and the entry id is the one used by tasks. Affects all scenarios (works for both models and the mini model).
4. **Pool name versus instance name.** Instances are `<pool name>_<k>`, taken from the entry `name` (for example `Clerk_0`, `Senior Officer_2`, with the space kept). Affects `resource` fields in all outputs.
5. **Where flows come from.** I build in/out flows from `sequenceFlow` `sourceRef`/`targetRef` and ignore `<incoming>`/`<outgoing>` child elements (spec section 2.1 does not say which is authoritative). Order of outgoing flows (used only for parallel gateway emission order) is document order. The published models appear consistent either way.
6. **Several `process` elements, nested content, and untouched unsupported elements.** I read the direct children of every `process` element and treat all of them as one model. Elements of other types (lanes, annotations, `userTask`, and so on) are ignored unless a `sequenceFlow` touches them, in which case the error is `unsupported_model`. Pharmacy contains `collaboration`, `laneSet`, `error` and a `messageEventDefinition` in its start event; these are ignored. Affects the 16 Pharmacy scenarios only if one disagrees.
7. **Probabilities that do not sum to 1 in the model file.** Spec 2.2 only demands the path set match. I require non-negative values with an exact sum of 1 and give `unsupported_model` otherwise, because otherwise "choose the first flow with u < cumulative" can select nothing. All published values sum to 1. None.
8. **Number formats.** `value` entries in the model may be numbers or numeric strings (accepted). Probabilities in the model may be decimal strings or JSON numbers; numbers are converted with their shortest decimal text (`Fraction(repr(x))`) so `0.2` means exactly 1/5. Decimal strings in interventions must match `digits[.digits]` (no sign, exponent, or fraction syntax); anything else is `invalid_intervention` or `invalid_scenario` (for override `u`). Whether JSON numbers are allowed for `factor` or routing values is not stated; I require strings. None.
9. **Calendars.** Windows with begin = end are empty and ignored; begin > end, an unknown weekday, or `from` after `to` is `unsupported_model`. `24:00:00` is accepted as end of day. A calendar that is missing or has no working time is `unsupported_model` (the spec is silent, and `next_open` would be undefined). Adjacent windows across midnight are treated as the same working set. Affects: only the mini and published models; none differ.
10. **`amount` below 1** (zero or negative) is `unsupported_model`; the spec is silent. None.
11. **Pool entries and task entries.** A task whose `resources` list does not have exactly one entry, or with two entries for one task, is `unsupported_model`. Extra entries for ids that are not tasks are ignored (like extra gateway probabilities). None.
12. **Normal quantile accuracy.** Section 5 allows 1e-9 absolute error for Phi and Phi_inv, but rounding to integer seconds can flip when x is within 1e-9 of a .5 boundary. `run.py` uses `erfc` and `statistics.NormalDist.inv_cdf`; the validator uses `erf` and bisection. They agree on every value in all 64 outputs. Different implementations could disagree on a very rare draw. Affects the `norm` tasks in Pharmacy scenarios.
13. **Clamping of quantiles.** For `norm` I clamp to `[ceil(lo), floor(max)]` with `lo = max(min, 0)` as written, and when the inverse CDF argument is exactly 0 or 1 I return the corresponding bound. For `fix`, `round_half_up(v)` with no clamp. None.
14. **Duplicate draw overrides for one identity.** Not specified; the last one wins. Override fields of wrong type give `invalid_scenario`. Overrides for the `interarrival` identity apply to base case arrivals. None.
15. **Interventions list that is not a list**, or an entry that is not an object, is `invalid_intervention`. Unknown extra keys inside an intervention or selector are ignored. A selector `visit` that is any integer is accepted (even 0 or negative; it simply matches nothing). `selector.from`/`to` may be any integer (negative allowed). None.
16. **`resource_add.count` upper bound.** Section 9.7 lists "a count above the pool's size" as invalid; I apply it only to `resource_unavailable` (selection of existing instances), not to `resource_add`. `resource_add.from` must be an integer >= 0 (negative would put `free_at` before t = 0), and `count >= 1`. `resource_unavailable.from` and `to` may be negative. Affects H04, P_*_resource_add only for count 1, within the pool size anyway.
17. **`resource_unavailable` with both or neither of `count` and `instances`**, an empty `instances` list, or an instance name from another pool is `invalid_intervention`. Duplicate names in `instances` are accepted. None.
18. **Removing and re-adding a case id.** `case_add` with an id equal to any base case id (even one that is also removed) is invalid. Removing the same case twice is accepted. None.
19. **Which intervention conflicts are "target" conflicts.** "Same family and target" is read as: the three duration types are one family keyed by task, the three timer types one family keyed by timer, `routing_set` keyed by gateway. Conflicts are detected only when two interventions match one actual activation (dynamic), not from overlapping selectors that never match. Resource and case-set families never conflict. None.
20. **Error precedence.** The spec does not rank errors. I check, in order: scenario structure (`invalid_scenario`), model loading (`unsupported_model`), all interventions (`invalid_intervention`), then dynamic errors in event-time order (`conflicting_interventions`, `visit_limit_exceeded`, `deadlock`). A missing or unreadable model file is treated as `unsupported_model`. If a run has several dynamic errors, the reported one depends on processing order and may differ between conforming implementations. None of the 64 outputs is an error.
21. **Visit limit.** I read "exceeds 100 visits" as the 101st activation is an error (100 are allowed). A cycle made only of pass-through (single-outflow exclusive) gateways has no visit counter and would never terminate; I stop after a very large number of token moves and report `visit_limit_exceeded`. None.
22. **Deadlock detection time.** I check for tokens left at parallel gateways after the whole simulation, for every case. A case with no token reaching any end event also gives `deadlock`.
23. **`end_event` when several end events are reached at the same latest time.** The spec does not say which; `run.py` picks the lexicographically smallest id, and the validator accepts any of the end events reached at that time. None (all models have one end event reachable per case at a time, or distinct times).
24. **Parallel join with several tokens per flow.** "The earliest on each flow" is implemented by token time. Because both implementations deliver tokens in simulated-time order while section 8 delivers in dispatch order, results could differ only when tokens of one case sit on the same join flow out of order; the spec says this cannot happen in supported models. None.
25. **Simultaneous token events and visit numbers.** If two tokens of one case reach the same task or timer at the same instant, visit numbering depends on processing order. Spec section 4 says this is causally ordered and does not occur in supported models. None.
26. **`u` output formatting.** "The draw as a double with 12 decimals": I use `'%.12f' % float(u)`, so an override such as `0.8413447` is written `0.841344700000` and a draw very close to 1 would round to `1.000000000000`.
27. **Pause semantics at removal edge.** A task that would finish exactly when a removal begins is not paused (its end equals the removal start); a task that would need the removed second pauses. This follows from `work_end`; stated only implicitly. Affects H02, H03.
28. **Instance ranking of added instances.** `free_at = from` is the raw `free_at` used in the tie-break (`s`, `free_at`, `k`), so an added instance with a large `from` loses ties against old instances free earlier. Follows directly from section 8 but not spelled out. Affects H04 and P_*_resource_add.
29. **Property 10.** The "does not change any evaluated value" wording cannot be decided from the output of a single run for resource interventions. The validator tests it only when it can prove a no-op: duration/timer/routing values equal to base at all matches, a removal that overlaps no working time, or a `resource_add` starting after the last task start of that pool. That covers H12, H13, H14 only; the other base-comparison scenarios are `not_applicable`.
30. **Property 8 and the base run.** P8 compares `u` for identities in both runs. The validator is not given the base scenario, so it cannot confirm "same overrides". For H07 (which adds overrides absent from the H01 base) the identities overridden only in H07 are skipped and listed under `skipped_overridden_here_only` in the report; they are still verified against the scenario's override list by the draw recomputation.

## C. Checks that the validator adds beyond section 12

- Output shape, field types, sort orders and `u` format.
- Draw set equals the set of activations; every `u` recomputed from seed/overrides.
- Every `service` and `delay` recomputed from section 5 and 9, and conflict detection.
- Minimality of `end` (the last second before `end` is working time, so a task does not report a later `end` than needed), which property 4 alone does not force for service 0 or for ends at window boundaries.
- Arrival times and case set recomputed from section 6.
- A literal replay of section 8 over the recorded activations (see item 1 about its one tie caveat).
